# NFC Habit Tags — Design

Date: 2026-11-14. Owner: Vineet (plus 2 friends as recipe authors). Working name: "NFC Habit Tags" (brand TBD).

## Intent

Atomic Habits argues you shape behaviour by shaping your environment. Today our environment is mostly our phone. This product lets someone stick cheap NFC tags around the house (desk, bed, door, gym bag) and tap their phone on them to switch the phone into the right mode for that place and time: desk = social apps blocked, bed at night = sleep mode, morning = exercise routine.

The product is a companion app per platform plus a catalog of ready-made **recipes** (what a tag does). Users pick a recipe, link it to any NFC tag they already own (e.g. bought on Amazon), and tap. Later the team sells its own pre-configured tags.

Success for v1: a new user with a blank tag goes from install to a working "desk focus" tag in under 2 minutes, on both iPhone and Android.

## Decisions made with Vineet

- **Companion app**, not a recipe-only website: the tag holds only a link; the app does the work, so one-tap setup needs our own app.
- **Both platforms. iPhone prioritised** (higher-paying users) but Android ships too.
- **Separate native apps**: Swift/SwiftUI for iOS, Kotlin/Jetpack Compose for Android, each with its own platform-native UI/UX. **Shared backend** for data and (later) payments.
- **Recipes are authored only by Vineet and friends** at launch. Users cannot publish.
- **Recipes are free** for now. Charging for recipes is a later phase; keep the data model ready for a price but build no purchasing for recipes.
- **Bring-your-own tag is a first-class path.** Selling the team's own pre-encoded tags is a later phase.

## Goals (v1)

1. Browse a curated recipe catalog in each app.
2. Install a recipe and link it to a tag (write a blank tag, or adopt a tag that already holds our link).
3. Tap a tag → recipe runs (or toggles off).
4. Recipes support time-of-day rules and tap-to-toggle / auto-off.
5. Authors can publish/edit recipes without an app release.

## Non-goals (v1)

- Paid recipes, creator payouts, user-published or shared recipes, ratings/reviews.
- Selling physical tags (phase 2 — but the tag URL format below must already support it).
- iPad, Apple Watch, Wear OS, web app (beyond a tiny landing/redirect page).
- Habit analytics beyond a simple per-tag tap log on device.

## Anti-goals (would be failure even if it works)

- Setup that feels like configuring Tasker. Every extra permission screen or manual step must be justified.
- Uploading the user's app usage or blocked-app lists to our servers. Personal config stays on device (sync of tag↔recipe links is fine).
- A block that the user can't escape in an emergency. There is always a way to end a block from the app.

## Approaches considered

- **A. React Native/Expo + native modules** — one UI codebase; native code only for blocking/NFC. Fastest for a small team.
- **B. Two native apps + shared backend (chosen by Vineet)** — the core features (Screen Time, NFC, DND, app blocking) are OS-specific anyway, so platform-native UX and fewer cross-platform surprises are worth building the UI twice.
- **C. Flutter + native modules** — same trade-off as A; only better with existing Flutter skills.
- Rejected: web/PWA (iOS web can't read NFC or block apps).

## How it works

### Tag ↔ app link

- Every tag holds one NDEF URI record: `https://<domain>/t/<tagId>` where `tagId` is a random, URL-safe ID (≥ 96 bits) generated by our system.
- The domain is configured for **iOS Universal Links** and **Android App Links**, so a tap opens our app directly when installed. When not installed, the URL serves a small web page that sends the user to the right store (this is what makes phase-2 sold tags work out of the box).
- **Writing a blank tag:** app generates `tagId`, writes the URL, records `tagId → recipe` locally.
- **Adopting a tag that already has our URL** (e.g. re-linking, or a phase-2 sold tag): app reads it and lets the user assign a recipe.
- Tags already holding someone else's data must be overwritten (with confirmation). Locked tags are reported as unusable.
- Tag-to-recipe mapping lives on the device; synced to the backend only when the user is signed in (so a new phone restores it).

### Tap behaviour per platform

- **iOS:** background tag reading shows a system banner; the user taps it, the app opens via Universal Link and runs the recipe. (One extra tap is unavoidable.) An in-app "Scan" button also works.
- **Android:** App Link opens the app (or a transparent activity) and runs the recipe immediately.

### Recipes

A recipe is **data, not code**: a versioned JSON document the apps interpret. Authors combine a fixed set of actions and rules the apps implement.

Shape (illustrative):

```json
{
  "id": "desk-deep-work",
  "schemaVersion": 1,
  "title": "Desk: Deep Work",
  "description": "...",
  "placementHint": "Stick under your desk edge",
  "mode": "toggle",              // "toggle" | "oneShot"
  "autoOffMinutes": 90,          // optional
  "rules": [
    { "when": { "time": "06:00-22:00" }, "actions": [ ... ] },
    { "when": { "time": "22:00-06:00" }, "actions": [ ... ] }
  ],
  "price": null                  // reserved for paid phase
}
```

v1 action set (each app declares which it supports; unsupported actions are shown as "not available on this phone" rather than silently skipped):

| Action | iOS | Android |
|---|---|---|
| Block app group (shield apps) | Screen Time (FamilyControls/ManagedSettings) | Accessibility service or usage-stats + overlay (builder decides; see Constraints) |
| Do Not Disturb / Focus on/off | Not possible directly; optional one-time Apple Shortcut the app helps install | NotificationManager with DND policy access |
| Start timer (with end notification) | yes | yes |
| Show checklist (e.g. morning routine steps) | yes | yes |
| Open another app / URL | via URL scheme / universal link where available | launch intent |
| Log habit (local tap log) | yes | yes |

**App groups are abstract in recipes** ("social", "video", "games", "messaging"):
- Android: the backend ships a curated package-name list per group; user can edit on install.
- iOS: Screen Time only gives opaque app tokens chosen by the user on their device, so on install the app shows Apple's app picker with guidance ("pick your social apps"). The chosen tokens are stored per group on device and reused by every recipe that names that group. They are never uploaded.

Rules: time windows (local time) choose which action list runs on a tap. `toggle` mode: tap once = on, tap again = off (off reverses what "on" did). `autoOffMinutes` ends it automatically.

The bed example becomes: night tap → sleep mode on (block apps + DND); morning tap (or auto-off at wake time) → sleep mode off + show morning checklist + open workout app.

### Backend (shared)

My call: **Supabase** (Postgres, auth, storage, edge functions). Reasons: cheap at small scale, native Swift and Kotlin SDKs, no server to run.

- `recipes` table (JSON document + metadata, `published` flag, `price` nullable, `minSchemaVersion`).
- `app_groups` table (group → Android package list, iOS guidance text).
- `user_tags` table (user_id, tagId, recipe_id, label) — only for signed-in users.
- Auth: **Sign in with Apple** and **Google**; the app works fully without an account (account only adds sync/restore).
- Recipe authoring: authors edit via the Supabase dashboard (or a minimal internal admin page — builder's call). Apps fetch the catalog and cache it for offline use.
- Landing/redirect page for `/t/<tagId>` and the `apple-app-site-association` / `assetlinks.json` files, hosted on the same domain (e.g. a static host).

### Payments (phase 2, not built in v1)

- Physical tags: web checkout (Stripe or Shopify) opened from the app; no Apple/Google fee applies to physical goods.
- Paid recipes later: must use Apple/Google in-app purchase (15% under small-business programs), unless recipes are bundled with our own tags (possible hardware exemption, App Review decides).

## Constraints and risks

- **Apple Family Controls distribution entitlement** must be requested from Apple before App Store release of app blocking. Takes weeks — apply at project start.
- **iOS cannot set Focus/DND from an app.** Only the optional Shortcut path.
- **iOS NFC banner tap** — one extra tap per use; can't be removed.
- **Android blocking via AccessibilityService** needs a Google Play policy declaration and can be rejected; the usage-stats + overlay approach is weaker but lower risk. Builder should pick after checking current Play policy.
- **Android OEM battery killers** (Xiaomi, Oppo, etc.) may stop background blocking; onboarding must guide users to exempt the app.
- NFC hardware: iPhone XS or newer for background reading; Android phones without NFC can't use the product (show this at install).
- Tag type: NTAG213/215/216 recommended; the app should say so.

## Calls made after builder review (Claude's calls — Vineet to check)

- **Android blocking: usage-stats + overlay from day one**, no AccessibilityService. Avoids the Play policy declaration risk; a block that kicks in within about a second is acceptable for a habit tool (it's a speed bump, not parental control).
- **tagId is generated on the phone** (random, ≥96 bits) in v1. No server registry yet. A tap on a tagId this phone doesn't know opens a "Set up this tag" flow, so a tag scanned by another person's phone simply gets linked on their phone too (tags are per-phone). Phase 2 adds a `tags` table of pre-provisioned IDs with a default recipe for sold tags.
- **Toggle state lives on the device**, per tag. Several recipes can be active at once; blocked apps are the union of all active recipes; turning one off removes only what it added. The home screen lists active modes with an "end now" button (the emergency escape).
- **Permissions are asked just in time**: Screen Time / usage access / DND access are requested only when the user installs a recipe that needs them, never all up front. Android DND is in v1 under this rule.
- **Schema versions:** a recipe needing a newer schema than the app supports is shown greyed out with "Update the app to use this".
- **Dev domain:** a throwaway domain is used for development and testing; no tag leaves the team until the real domain is set (see open items).
